## 1. Что делает программа

Программа получает папку с Java-проектом, находит в ней все файлы `.java` и в каждом ищет объявления классов и интерфейсов, например:

```java
class Dog extends Animal implements Runnable { ... }
```

Из этой строки следует: у `Dog` два родителя, `Animal` и `Runnable`. Программа строит **обратный индекс**: для каждого родителя список его детей. Печатается так:

```
Animal <- Dog
Runnable <- Dog
```

Обычный индекс отвечал бы на вопрос «кто родитель у Dog?». Обратный отвечает на вопрос «кто наследует Animal?».

Вся логика поиска пришла из ЛР2. В ЛР3 добавилось одно: **каждый файл обрабатывается в отдельном потоке**.

## 2. Что такое поток и зачем он нужен

### Один поток

Обычная программа выполняет команды строго по очереди. Первая закончилась, началась вторая. Представьте одного сотрудника, который проверяет документы по одному. Такой «исполнитель» называется **потоком** (`Thread`). Тот, с которого начинается программа (метод `main`), называется **главным потоком**.

### Несколько потоков

Внутри одной программы можно запустить дополнительные потоки. Они работают **одновременно** (на многоядерном процессоре действительно параллельно). Это как нанять ещё сотрудников: 10 000 документов, 10 000 сотрудников, все проверяют сразу.

Зачем это нужно вообще: чтобы быстрее выполнять тяжёлую работу и не простаивать, когда одни операции ждут диск или сеть. В этой лабораторной цель учебная: научиться запускать потоки и дожидаться их завершения.

### Главная опасность: общие данные

Сотрудники мешают друг другу, если пишут в **одно и то же место**. Представьте одну общую тетрадь, в которую 10 000 человек одновременно вписывают строки. Записи затрут друг друга, часть потеряется, результат будет испорчен. Это называется **гонкой данных** (race condition).

Есть два способа жить с этим:

- Поставить на тетрадь замок: писать может только один сотрудник за раз (`synchronized`, `ReentrantLock`). Это **ЛР4**.
- Раздать каждому **свою тетрадь**, чтобы пересекаться было негде. Это **ЛР3**. Задание прямо говорит: «Взаимодействия потоков не требуется!».

В ЛР3 выбран второй путь: каждый поток пишет в свой индекс, а потом главный поток объединяет все индексы в один.

### Ожидание завершения потоков

Когда главный поток запустил потоки, он не знает, когда они закончат. Если он сразу начнёт печатать результат, тот будет неполным. Нужно **дождаться** всех. Для этого в задании предложены `join()` или `CountDownLatch`. Здесь используется `CountDownLatch`, подробнее в разделе 5.

## 3. Основы Java, которые встречаются в коде

Этот раздел можно читать как словарь. Все понятия дальше разбираются на конкретных строках.

### Класс и метод

Вся Java-программа состоит из **классов**. Класс здесь `InheritanceIndexThreads`. Внутри класса лежат **методы** (функции): `main`, `processFile`, `addParents` и другие. Файл должен называться так же, как публичный класс: `InheritanceIndexThreads.java`.

### `main`

С метода `public static void main(String[] args)` начинается выполнение программы. `args` это массив строк с аргументами командной строки. Если запустить `java InheritanceIndexThreads папка`, то `args[0]` будет `"папка"`.

### Модификаторы `public`, `private`, `static`, `final`

- `public` доступно отовсюду, `private` доступно только внутри этого класса.
- `static` принадлежит самому классу, а не конкретному объекту. Вызывать такой метод можно без создания объекта. В программе все методы `static`, объектов самого `InheritanceIndexThreads` мы не создаём.
- `final` значение после присвоения менять нельзя. Для константы это подходит.
- `void` метод ничего не возвращает.

### Переменная и тип

Java требует указывать тип переменной:

```java
int i = 0;                   // целое число
String text;                 // строка
Path root = Path.of("...");  // путь к файлу или папке
```

### `null`

Специальное значение «ничего нет». Если переменная содержит `null`, вызвать у неё метод нельзя, будет ошибка. Поэтому в коде есть проверка `if (parentsText == null)`.

### Массив и список

- **Массив** фиксированного размера: `String[] args`. Доступ к элементу через `args[0]`.
- **Список** `List<...>` растущая коллекция. Размер можно менять. Доступ к элементу через метод `get`, а не через квадратные скобки. Нумерация **с нуля**: первый элемент `get(0)`, последний `get(size() - 1)`.

Основные методы списка, которые встречаются в коде:

| Метод | Что делает |
|---|---|
| `list.add(x)` | добавить элемент в конец |
| `list.get(i)` | взять элемент с номером `i` |
| `list.size()` | сколько элементов |
| `list.addAll(other)` | добавить все элементы другого списка |

### `List` и `ArrayList`: интерфейс и реализация

`List` это **интерфейс**: описание того, что список умеет. `ArrayList` это **конкретная реализация**. Создают конкретный `ArrayList`, а тип переменной пишут по интерфейсу:

```java
List<String> names = new ArrayList<>();
```

Так принято, потому что программе важно, что это «какой-то список». Конкретную реализацию можно заменить, не меняя остальной код. Аналогично `Map` интерфейс, а `TreeMap` реализация.

### Обобщения (generics): угловые скобки

В `List<String>` часть `<String>` указывает, что в этом списке лежат строки. Это называется **обобщением** (generics). Они могут быть вложены:

```java
Map<String, List<String>>
```

Читается так: **словарь**, где ключ строка, а значение **список строк**. Именно такой тип у нашего индекса: ключ это имя родителя, значение список его детей.

В записи `new ArrayList<>()` пустые скобки `<>` (называются «ромб») означают «компилятор, определи тип сам по левой части».

### `Map`: словарь

`Map<K, V>` хранит пары «ключ значение»: по ключу быстро находится значение. Основные методы:

| Метод | Что делает |
|---|---|
| `map.put(k, v)` | положить значение `v` по ключу `k` (старое заменится) |
| `map.get(k)` | вернуть значение по ключу, или `null`, если ключа нет |
| `map.getOrDefault(k, d)` | вернуть значение по ключу, или `d`, если ключа нет |
| `map.forEach((k, v) -> ...)` | выполнить действие для каждой пары |

`TreeMap` это `Map`, который хранит ключи **отсортированными** по алфавиту. Благодаря этому итоговый вывод сразу упорядочен.

### `new`

Ключевое слово создания объекта: `new ArrayList<>()`, `new TreeMap<>()`, `new Thread(...)`.

### Цикл `for`

```java
for (int i = 0; i < n; i++) { ... }
```

Три части в скобках:

1. `int i = 0` начальное значение счётчика;
2. `i < n` условие продолжения: пока истинно, цикл идёт;
3. `i++` что делать после каждого шага (`i++` означает «увеличить `i` на 1»).

Если `n = 3`, тело выполнится для `i = 0, 1, 2`.

Есть и другая форма, **for-each**: `for (Map<...> partial : partialIndexes)`. Она перебирает элементы коллекции по очереди, номер элемента не нужен.

### Лямбда-выражение

Лямбда это короткая запись маленькой функции без имени. Форма: `(параметры) -> результат_или_блок`.

```java
p -> Files.isRegularFile(p)        // «принимает p, возвращает результат проверки»
() -> { ... }                      // «без параметров, выполнить блок»
(parent, children) -> { ... }      // «два параметра»
```

Лямбду можно передать в метод как значение: «вот действие, которое нужно выполнить». Именно так мы передаём потоку код, который ему выполнять.

**Важное ограничение.** Лямбда может использовать переменные снаружи, только если они **не меняются после присвоения** (это называется *effectively final*). Если переменная меняется (как счётчик `i` в цикле), использовать её внутри лямбды нельзя, будет ошибка компиляции.

### Ссылка на метод

Запись `String::trim` это сокращение лямбды `s -> s.trim()`.

### Stream API

Stream это конвейер обработки данных: «взять элементы, отфильтровать, преобразовать, собрать результат».

```java
paths.filter(...).map(...).collect(...)
```

Основные операции:

| Операция | Что делает |
|---|---|
| `filter(условие)` | оставляет элементы, для которых условие истинно |
| `map(функция)` | превращает каждый элемент в другой |
| `sorted()` | сортирует |
| `distinct()` | убирает повторы |
| `forEach(действие)` | выполняет действие для каждого элемента |
| `collect(...)` | собирает результат в коллекцию или строку |

### Исключения

Когда операция может не получиться (файл недоступен), Java «выбрасывает исключение». Его нужно либо поймать, либо объявить:

```java
try {
    ... // опасная операция
} catch (IOException e) {
    ... // что делать при ошибке
}
```

Либо переложить ответственность на вызывающего: `void main() throws IOException`.

Блок `finally` выполняется **всегда**: и после успеха, и после ошибки.

### `System.out` и `System.err`

`System.out.println(...)` печатает в обычный вывод. `System.err.println(...)` в поток ошибок. Для пользователя в консоли они выглядят похоже, но это разные потоки, и ошибки удобно отделять от результата.

## 4. Полный код

```java
import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.ArrayList;
import java.util.Arrays;
import java.util.List;
import java.util.Map;
import java.util.TreeMap;
import java.util.concurrent.CountDownLatch;
import java.util.regex.Matcher;
import java.util.regex.Pattern;
import java.util.stream.Collectors;
import java.util.stream.Stream;

public class InheritanceIndexThreads {

    private static final Pattern DECLARATION = Pattern.compile(
        "\\b(class|interface)\\s+(\\w+)\\s*"
        + "(?:extends\\s+([^{]+?))?\\s*"
        + "(?:implements\\s+([^{]+?))?\\s*"
        + "(?:permits\\s+[^{]+?)?\\s*\\{"
    );

    public static void main(String[] args) throws IOException, InterruptedException {
        Path root = Path.of(args.length > 0 ? args[0] : ".");

        List<Path> javaFiles;
        try (Stream<Path> paths = Files.walk(root)) {
            javaFiles = paths
                    .filter(p -> Files.isRegularFile(p))
                    .filter(p -> p.toString().endsWith(".java"))
                    .collect(Collectors.toList());
        }

        // У каждого файла (потока) свой отдельный индекс: потоки ничего не разделяют
        List<Map<String, List<String>>> partialIndexes = new ArrayList<>();
        for (int i = 0; i < javaFiles.size(); i++) {
            partialIndexes.add(new TreeMap<>());
        }

        CountDownLatch latch = new CountDownLatch(javaFiles.size());
        for (int i = 0; i < javaFiles.size(); i++) {
            Path file = javaFiles.get(i);
            Map<String, List<String>> localIndex = partialIndexes.get(i);
            new Thread(() -> {
                try {
                    processFile(file, localIndex);
                } finally {
                    latch.countDown();
                }
            }).start();
        }
        latch.await();

        Map<String, List<String>> index = new TreeMap<>();
        for (Map<String, List<String>> partial : partialIndexes) {
            partial.forEach((parent, children) -> {
                List<String> all = index.getOrDefault(parent, new ArrayList<>());
                all.addAll(children);
                index.put(parent, all);
            });
        }

        index.forEach((parent, children) -> {
            String line = children.stream()
                    .distinct()
                    .sorted()
                    .collect(Collectors.joining(", "));
            System.out.println(parent + " <- " + line);
        });
    }

    private static void processFile(Path file, Map<String, List<String>> index) {
        String text;
        try {
            text = Files.readString(file);
        } catch (IOException e) {
            System.err.println("Не удалось прочитать файл: " + file);
            return;
        }

        text = removeComments(text);
        text = removeGenerics(text);

        Matcher m = DECLARATION.matcher(text);
        while (m.find()) {
            String child = m.group(2);
            addParents(index, child, m.group(3));
            addParents(index, child, m.group(4));
        }
    }

    private static void addParents(Map<String, List<String>> index, String child, String parentsText) {
        if (parentsText == null) {
            return;
        }
        Arrays.stream(parentsText.split(","))
                .map(String::trim)
                .filter(name -> !name.isEmpty())
                .map(name -> name.substring(name.lastIndexOf('.') + 1))
                .forEach(parent -> {
                    List<String> children = index.getOrDefault(parent, new ArrayList<>());
                    children.add(child);
                    index.put(parent, children);
                });
    }

    private static String removeComments(String text) {
        return text.replaceAll("(?s)/\\*.*?\\*/", "").replaceAll("//.*", "");
    }

    private static String removeGenerics(String text) {
        String previous;
        do {
            previous = text;
            text = text.replaceAll("<[^<>]*>", "");
        } while (!text.equals(previous));
        return text;
    }
}
```

### 5.2. Объявление класса

### 5.3. Регулярное выражение

```java
private static final Pattern DECLARATION = Pattern.compile(
    "\\b(class|interface)\\s+(\\w+)\\s*"
    + "(?:extends\\s+([^{]+?))?\\s*"
    + "(?:implements\\s+([^{]+?))?\\s*"
    + "(?:permits\\s+[^{]+?)?\\s*\\{"
);
```

- `private static final` значит: константа, принадлежит классу, значение нельзя менять, видна только внутри класса.
- `Pattern.compile(...)` превращает текст регулярки в готовый к работе шаблон. Это делается **один раз**, а не в каждом потоке заново. Объект `Pattern` потокобезопасен: его могут одновременно использовать разные потоки.
- Регулярка записана несколькими строками, склеенными знаком `+`. Это просто для читаемости, Java склеит их в одну строку.
- В Java-строке символ `\` нужно писать как `\\`. Реальный шаблон выглядит так: `\b(class|interface)\s+(\w+)\s*(?:extends\s+([^{]+?))?\s*(?:implements\s+([^{]+?))?\s*(?:permits\s+[^{]+?)?\s*\{`.

Разбор шаблона по кусочкам:

| Кусок | Что означает |
|---|---|
| `\b` | граница слова: перед `class` нет буквы. Чтобы не найти слово `class` внутри другого, например в `subclass` |
| `(class\|interface)` | **группа 1**: слово `class` или `interface` |
| `\s+` | один или больше пробельных символов (пробел, таб, перенос строки) |
| `(\w+)` | **группа 2**: имя класса. `\w` это буква, цифра или `_`, `+` значит «одна или больше» |
| `\s*` | ноль или больше пробельных символов |
| `(?:extends\s+([^{]+?))?` | необязательный блок `extends ...` (подробнее ниже) |
| `(?:implements\s+([^{]+?))?` | необязательный блок `implements ...` |
| `(?:permits\s+[^{]+?)?` | **новое:** необязательный блок `permits ...` |
| `\s*\{` | пробелы и открывающая фигурная скобка тела класса. `\{` значит буквальную `{` |

Подробнее про блок `extends`:

- `(?: ... )` скобки только для группировки, **не создают номерную группу**.
- `?` после закрывающей скобки значит «этот блок может отсутствовать».
- Внутри `([^{]+?)` обычная скобка, создаёт **группу 3** (список родителей).
- `[^{]` любой символ, кроме `{`. `+?` один или больше, **лениво**.

**Что значит «лениво».** `+` («жадно») берёт максимум символов. `+?` («лениво») берёт минимум и расширяется, только если дальше шаблон не совпадает. Для `class C extends A implements B {` ленивая группа 3 остановится на `A`, потому что после неё уже можно сопоставить `implements`. Жадная съела бы `A implements B`.

**Нумерация групп** идёт по порядку открывающих обычных скобок `(`, а скобки вида `(?:` не считаются. Поэтому: 1 = `class|interface`, 2 = имя, 3 = родители из `extends`, 4 = список из `implements`. У блока `permits` группы нет, потому что нам его содержимое не нужно, мы его лишь пропускаем.

**Зачем `permits`.** В Java 17+ есть sealed-классы:

```java
sealed interface HttpStatusCode extends Serializable permits DefaultHttpStatusCode, HttpStatus {
```

Без блока `permits` ленивая группа 3 расширялась бы до `{` и захватила бы `Serializable permits DefaultHttpStatusCode, HttpStatus`. В индексе появились бы битые записи и ложные «родители». Теперь шаблон знает про `permits`, и группа 3 заканчивается перед ним.

### 5.4. Метод `main`

```java
public static void main(String[] args) throws IOException, InterruptedException {
```

- `public static void main(String[] args)` стандартная точка входа.
- `throws IOException, InterruptedException` метод может выбросить эти исключения и не ловит их сам. `IOException` может прийти от `Files.walk`. `InterruptedException` (**новое**) может прийти от `latch.await()`: это исключение возникает, если ожидающий поток кто-то прервал. Без `throws` код не скомпилируется.

#### Корневая папка

```java
Path root = Path.of(args.length > 0 ? args[0] : ".");
```

- `args.length` число переданных аргументов.
- `условие ? a : b` короткий `if/else`: если аргументы есть, взять `args[0]`, иначе `"."`.
- `"."` текущая папка.
- `Path.of(...)` превращает строку в объект `Path`.

#### Сбор файлов

```java
List<Path> javaFiles;
```

Объявляется переменная для списка путей. Значение присвоим ниже. Объявление вынесено наружу блока `try`, чтобы переменная была видна и после него.

```java
try (Stream<Path> paths = Files.walk(root)) {
```

- `Files.walk(root)` рекурсивно обходит папку `root` и все вложенные и возвращает **поток** (`Stream<Path>`) путей ко всем файлам и папкам.
- `try (...)` в такой форме называется try-with-resources. Обход папок держит открытые системные ресурсы. Конструкция гарантирует, что `paths` будет закрыт автоматически, когда блок закончится.

```java
    javaFiles = paths
            .filter(p -> Files.isRegularFile(p))
            .filter(p -> p.toString().endsWith(".java"))
            .collect(Collectors.toList());
}
```

Конвейер:

1. `.filter(p -> Files.isRegularFile(p))` оставляет только обычные файлы, отсеивает папки. Лямбда принимает путь `p` и возвращает `true/false`.
2. `.filter(p -> p.toString().endsWith(".java"))` оставляет пути, которые заканчиваются на `.java`. `p.toString()` превращает путь в строку, `endsWith` проверяет окончание.
3. `.collect(Collectors.toList())` собирает оставшиеся пути в обычный список.

После блока в `javaFiles` лежат пути ко всем `.java`-файлам проекта.

#### Создание отдельных индексов

```java
List<Map<String, List<String>>> partialIndexes = new ArrayList<>();
```

Читается изнутри наружу:

- `Map<String, List<String>>` словарь «имя родителя список имён детей». Это **один индекс**, одна «тетрадь».
- `List<...>` вокруг него **список таких индексов**, «стопка тетрадей».
- `new ArrayList<>()` создаётся пустой список.

```java
for (int i = 0; i < javaFiles.size(); i++) {
    partialIndexes.add(new TreeMap<>());
}
```

Цикл выполняется по разу на каждый файл. На каждом шаге `new TreeMap<>()` создаёт **пустой** словарь, `partialIndexes.add(...)` кладёт его в конец списка. Если файлов 10 000, получится 10 000 пустых индексов. Индекс с номером `i` будет принадлежать файлу с номером `i`.

**Зачем создавать их заранее, отдельным циклом.** Все индексы появляются **до** запуска потоков. Список индексов создаёт и меняет только главный поток. Когда потоки уже работают, список никто не изменяет. Если бы потоки сами добавляли себе индекс в общий список, это была бы запись в общее место из разных потоков, то есть то самое взаимодействие, которого в ЛР3 быть не должно.

#### Защёлка

```java
CountDownLatch latch = new CountDownLatch(javaFiles.size());
```

`CountDownLatch` («защёлка с обратным отсчётом») это счётчик, который можно только уменьшать:

- при создании в него записывается число, здесь **количество файлов**;
- метод `countDown()` уменьшает счётчик на 1;
- метод `await()` **блокирует** вызвавший его поток, пока счётчик не станет 0.

Идея: каждый файл это одна задача, каждая завершившаяся задача вычитает единицу, главный поток ждёт, пока вычтут все.

#### Запуск потоков

```java
for (int i = 0; i < javaFiles.size(); i++) {
```

Цикл по номерам файлов. Нужен именно номер `i`, потому что по нему мы свяжем файл с его индексом.

```java
    Path file = javaFiles.get(i);
```

Эту строку полезно разобрать подробно.

- `javaFiles` это `List<Path>` (список путей), не массив. У списка нет записи `javaFiles[i]`.
- Чтобы взять элемент списка по номеру, используется метод `get(i)`. Нумерация **с нуля**: `get(0)` первый файл, `get(1)` второй и так далее.
- Результат `get(i)` это объект типа `Path`, поэтому слева `Path file`.
- Итого: «взять `i`-й файл из списка и запомнить его в переменной `file`».

**Зачем отдельная переменная `file`, а не использовать `javaFiles.get(i)` прямо внутри потока.** Код потока ниже оформлен лямбдой. Лямбда выполняется **позже и в другом потоке**, а переменная `i` к тому моменту уже изменится (цикл продолжается). Поэтому Java запрещает использовать `i` внутри лямбды. Переменная `file`, наоборот, создаётся заново на каждом шаге цикла и больше не меняется, её можно передать в лямбду. В ней фиксируется «именно этот файл для именно этого потока».

```java
    Map<String, List<String>> localIndex = partialIndexes.get(i);
```

Тут то же самое, только для индексов: берётся `i`-й индекс из списка индексов. Теперь у нас есть пара: файл номер `i` и **его собственный** индекс номер `i`. Название `localIndex` («локальный индекс») подчёркивает, что он принадлежит только одному потоку.

Заметьте: индекс из списка достаёт **главный поток**, а в поток передаётся уже готовая ссылка на конкретный индекс. Сам поток в общий список не заглядывает.

```java
    new Thread(() -> {
```

- `new Thread(...)` создаёт объект-поток. В скобках передаётся код, который он должен выполнить.
- `() -> { ... }` лямбда без параметров. Её тело и есть работа потока.
- Тип такого кода называется `Runnable`.

```java
        try {
            processFile(file, localIndex);
        } finally {
            latch.countDown();
        }
```

- Поток вызывает `processFile`, передавая свой файл и свой индекс. Это основная работа.
- `finally` выполняется **всегда**. Поэтому `latch.countDown()` вызовется, даже если `processFile` выбросит неожиданное исключение. Если бы его не было, счётчик остался бы больше нуля и главный поток завис бы на `await()` навсегда.

```java
    }).start();
```

- Закрывающая `}` завершает тело лямбды, `)` закрывает вызов `new Thread(...)`.
- `.start()` **запускает** поток. С этого момента он работает параллельно с главным, а главный сразу идёт дальше по циклу и запускает следующий.
- Важно не перепутать: метод `.run()` выполнил бы код в текущем потоке, без параллельности. Для запуска нового потока нужен именно `.start()`.

```java
}
latch.await();
```

- Когда цикл закончился, запущены все потоки.
- `latch.await()` останавливает главный поток, пока счётчик не дойдёт до нуля, то есть пока все потоки не завершат свою работу. Это замена вызова `join()` для каждого потока по отдельности.
- Побочная польза: `await()` гарантирует, что всё, что потоки записали в свои индексы, **видно** главному потоку. Без такой гарантии Java формально не обещает, что запись одного потока станет видна другому.
- Именно `await()` может выбросить `InterruptedException`, потому и `throws` в заголовке `main`.

#### Объединение результатов

К этому моменту все потоки закончили. Дальше работает **только главный поток**, и никакой гонки данных нет.

```java
Map<String, List<String>> index = new TreeMap<>();
```

Создаётся итоговый индекс. Он пока пустой. `TreeMap` хранит ключи отсортированными по алфавиту.

```java
for (Map<String, List<String>> partial : partialIndexes) {
```

Цикл for-each: по очереди берётся каждый частичный индекс из списка в переменную `partial`.

```java
    partial.forEach((parent, children) -> {
```

`Map.forEach` проходит по всем парам словаря. Для каждой пары вызывается лямбда с двумя параметрами: `parent` (ключ, имя родителя) и `children` (значение, список его детей **в этом файле**).

```java
        List<String> all = index.getOrDefault(parent, new ArrayList<>());
```

Из итогового индекса берётся список детей этого родителя, накопленный из прошлых файлов. Если родителя там ещё нет, возвращается новый пустой список (`getOrDefault`: «верни значение по ключу, а если его нет, верни вот это»).

```java
        all.addAll(children);
```

В этот список добавляются все дети из текущего файла.

```java
        index.put(parent, all);
```

Список кладётся обратно в итоговый индекс. Это обязательно: `getOrDefault` **не сохраняет** значение по умолчанию в словарь, он только возвращает его. Если родитель был новым, без `put` пустой список с добавленными детьми просто потерялся бы.

Почему `index` можно использовать внутри лямбды, хотя мы его меняем: переменная `index` не получает нового значения, она всё время ссылается на один и тот же словарь. Мы меняем **содержимое** словаря, а не саму ссылку. Для лямбды важно только, что ссылка не переприсваивается.

#### Вывод

```java
index.forEach((parent, children) -> {
```

Снова проход по парам, теперь уже итогового индекса. Благодаря `TreeMap` ключи идут в алфавитном порядке.

```java
    String line = children.stream()
            .distinct()
            .sorted()
            .collect(Collectors.joining(", "));
```

Конвейер над списком детей:

1. `children.stream()` превращает список в поток.
2. `.distinct()` (**новое**) убирает повторяющиеся имена. Повторы возникают, потому что ключ это простое имя класса, и в большом проекте есть одноимённые классы в разных пакетах.
3. `.sorted()` сортирует по алфавиту.
4. `.collect(Collectors.joining(", "))` склеивает элементы в одну строку через запятую с пробелом.

```java
    System.out.println(parent + " <- " + line);
```

Печатается строка вида `Animal <- Cat, Dog`. Оператор `+` для строк склеивает их.

### 5.5. Метод `processFile`

```java
private static void processFile(Path file, Map<String, List<String>> index) {
```

Обрабатывает **один** файл. Получает путь к файлу и индекс, в который нужно записывать результат. Метод `private` (виден только внутри класса), `static`, `void` (ничего не возвращает).

Ключевое свойство для многопоточности: метод **не использует никаких общих изменяемых данных**. Он работает только с тем, что ему передали, и со своими локальными переменными. Поэтому его можно безопасно запускать из многих потоков, каждый со своим `index`.

```java
String text;
try {
    text = Files.readString(file);
} catch (IOException e) {
    System.err.println("Не удалось прочитать файл: " + file);
    return;
}
```

- `Files.readString(file)` читает весь файл в одну строку.
- Если не получилось (нет прав, неподходящая кодировка), выбрасывается `IOException`. Блок `catch` его ловит, пишет сообщение в поток ошибок и `return` завершает метод. Остальные файлы и потоки продолжают работу. Один проблемный файл не ломает всю программу.

```java
text = removeComments(text);
text = removeGenerics(text);
```

Очистка текста перед поиском (подробно в 5.7 и 5.8): убрать комментарии и угловые скобки обобщений.

```java
Matcher m = DECLARATION.matcher(text);
```

Создаётся «поисковик» `m`, который применяет шаблон `DECLARATION` к тексту этого файла. `Pattern` общий для всех потоков, а `Matcher` хранит внутреннее состояние поиска («где я остановился»). Поэтому он **не потокобезопасен**, и у каждого вызова `processFile`, то есть у каждого потока, свой `Matcher`.

```java
while (m.find()) {
```

`m.find()` ищет следующее совпадение с шаблоном. Возвращает `true`, если нашёл. Цикл `while` повторяется, пока находятся новые объявления.

```java
    String child = m.group(2);
```

`m.group(2)` возвращает то, что совпало с группой 2 шаблона, то есть **имя класса** (ребёнка).

```java
    addParents(index, child, m.group(3));
    addParents(index, child, m.group(4));
```

Родители записываются в индекс: сначала из `extends` (группа 3), потом из `implements` (группа 4). Любая из групп может быть `null`, если блока в объявлении не было. Метод `addParents` это учитывает.

### 5.6. Метод `addParents`

```java
private static void addParents(Map<String, List<String>> index, String child, String parentsText) {
```

Принимает индекс, имя ребёнка и строку с родителями, например `"Animal"` или `"Runnable, Serializable"`.

```java
    if (parentsText == null) {
        return;
    }
```

Если блока `extends` или `implements` не было, `parentsText` равен `null`. Тогда делать нечего, метод выходит.

```java
    Arrays.stream(parentsText.split(","))
```

- `parentsText.split(",")` режет строку по запятым и возвращает **массив** строк. Из `"A, B, C"` получится `["A", " B", " C"]` (обратите внимание на пробелы).
- `Arrays.stream(...)` превращает массив в поток для дальнейшей обработки.

```java
            .map(String::trim)
```

`trim()` убирает пробелы и переносы строк по краям. Запись `String::trim` это краткая форма лямбды `s -> s.trim()`. После этого `" B"` превращается в `"B"`.

```java
            .filter(name -> !name.isEmpty())
```

Оставляет только непустые строки. Знак `!` значит «не». Пустая строка может получиться, например, если в тексте лишняя запятая.

```java
            .map(name -> name.substring(name.lastIndexOf('.') + 1))
```

Убирает пакет из полного имени. Например, `java.io.Serializable` должно стать `Serializable`.

- `name.lastIndexOf('.')` позиция **последней** точки в строке, или `-1`, если точки нет.
- `+ 1` позиция символа сразу после точки.
- `name.substring(k)` берёт кусок строки от позиции `k` до конца.
- Если точки нет, получится `substring(-1 + 1) = substring(0)`, то есть вся строка целиком. Это удобный приём, который работает в обоих случаях.

```java
            .forEach(parent -> {
                List<String> children = index.getOrDefault(parent, new ArrayList<>());
                children.add(child);
                index.put(parent, children);
            });
```

Для каждого родителя:

1. взять из индекса его список детей (или новый пустой, если родителя ещё нет);
2. добавить в него `child`;
3. положить список обратно в индекс (`put`), чтобы новый список не потерялся.

Результат: для `class C extends A implements B, D` в индексе появятся записи `A <- [C]`, `B <- [C]`, `D <- [C]`.

### 5.7. Метод `removeComments`

```java
private static String removeComments(String text) {
    return text.replaceAll("(?s)/\\*.*?\\*/", "").replaceAll("//.*", "");
}
```

Зачем нужен: чтобы слова `class` в комментариях, например `// this class extends Foo`, не попали в индекс.

`replaceAll(регулярка, замена)` заменяет все совпадения регулярки на текст замены. Здесь замена пустая `""`, то есть совпадения просто удаляются. Вызовы идут цепочкой: результат первой замены сразу получает вторую.

Первая замена, `"(?s)/\\*.*?\\*/"`, то есть `(?s)/\*.*?\*/`, убирает **блочные** комментарии `/* ... */`:

- `/\*` буквальные символы `/*` (звёздочку надо экранировать, потому что в регулярках `*` особый символ);
- `.*?` любые символы, **лениво** (минимально);
- `\*/` буквальные символы `*/`;
- `(?s)` включает режим, в котором `.` совпадает и с **переносом строки**. Без него многострочные комментарии не удалились бы;
- ленивость `*?` нужна, чтобы удалялся каждый комментарий по отдельности. Жадная версия вырезала бы всё от первого `/*` до **последнего** `*/` в файле, вместе с кодом.

Вторая замена, `"//.*"`, убирает **однострочные** комментарии: от `//` до конца строки (без `(?s)` точка не захватывает перенос строки).

Это упрощённый подход. Например, текст `"http://example.com"` в строковом литерале тоже обрежется до конца строки. Для поиска объявлений классов это не мешает.

### 5.8. Метод `removeGenerics`

```java
private static String removeGenerics(String text) {
    String previous;
    do {
        previous = text;
        text = text.replaceAll("<[^<>]*>", "");
    } while (!text.equals(previous));
    return text;
}
```

Зачем нужен: в объявлении `class A extends B<String, Integer>` внутри угловых скобок есть **запятая**. Метод `addParents` режет список родителей по запятым и принял бы `Integer>` за отдельного родителя. Поэтому угловые скобки вместе с содержимым удаляются.

- Регулярка `<[^<>]*>` находит `<`, затем любое количество символов, **не являющихся** `<` или `>`, затем `>`. Значит, она находит только **самые внутренние** скобки.
- Вложенные случаи убираются за несколько проходов. Пример `Map<String, List<String>>`:
  - проход 1: внутренняя пара `<String>` удалена, остаётся `Map<String, List>`;
  - проход 2: теперь `<String, List>` не содержит других скобок, удалена, остаётся `Map`;
  - проход 3: ничего не меняется, цикл заканчивается.
- Конструкция `do { ... } while (условие)` выполняет тело минимум один раз, а потом повторяет, пока условие истинно. Условие `!text.equals(previous)` значит «текст изменился за последний проход».
- Переменная `previous` запоминает текст до очередной замены, чтобы сравнить с результатом.

Побочный эффект: выражение вроде `if (a < b && c > d)` тоже может быть вырезано как «обобщение». Для поиска объявлений классов это безвредно.

## 6. Пример выполнения на трёх файлах

Пусть в папке три файла:

- `Dog.java`: `class Dog extends Animal { }`
- `Cat.java`: `class Cat extends Animal implements Runnable { }`
- `Pet.java`: `interface Pet extends Runnable { }`

**Шаг 1.** Главный поток собирает `javaFiles`: `[Dog.java, Cat.java, Pet.java]`, размер 3.

**Шаг 2.** Создаётся три пустых индекса: `partialIndexes = [{}, {}, {}]`. Защёлка `latch` со счётчиком 3.

**Шаг 3.** Цикл запускает три потока:

| `i` | `file` | `localIndex` |
|---|---|---|
| 0 | `Dog.java` | первый пустой индекс |
| 1 | `Cat.java` | второй пустой индекс |
| 2 | `Pet.java` | третий пустой индекс |

**Шаг 4.** Потоки работают одновременно и независимо. После их работы:

| Индекс | Содержимое |
|---|---|
| 0 | `{Animal: [Dog]}` |
| 1 | `{Animal: [Cat], Runnable: [Cat]}` |
| 2 | `{Runnable: [Pet]}` |

Каждый поток закончил и вызвал `countDown()`. Счётчик пошёл `3, 2, 1, 0`.

**Шаг 5.** Когда счётчик достиг 0, `await()` отпускает главный поток.

**Шаг 6.** Главный поток объединяет индексы в один:

- из индекса 0: `Animal <- [Dog]`;
- из индекса 1: `Animal` получает ещё `Cat`, а `Runnable <- [Cat]`;
- из индекса 2: `Runnable` получает ещё `Pet`.

Итог: `{Animal: [Dog, Cat], Runnable: [Cat, Pet]}`. Порядок внутри списка зависит от порядка обхода файлов, но при выводе есть `sorted()`.

**Шаг 7.** Вывод (ключи отсортированы благодаря `TreeMap`, дети благодаря `sorted()`):

```
Animal <- Cat, Dog
Runnable <- Cat, Pet
```

## 7. Почему не нужен `synchronized`

Синхронизация нужна, когда **несколько потоков меняют одни и те же данные**. В этой программе такого нет:

| Данные | Кто с ними работает |
|---|---|
| `localIndex` (свой для каждого потока) | пишет только свой поток, больше никто |
| `Matcher` | создаётся внутри `processFile`, у каждого потока свой |
| Локальные переменные (`text`, `child` и т.д.) | у каждого потока свои |
| `DECLARATION` (общий `Pattern`) | потоки только **читают**, а сам `Pattern` неизменяемый и потокобезопасный |
| `partialIndexes` (список индексов) | меняет только главный поток, до запуска потоков |
| Итоговый `index` | создаётся и заполняется только главным потоком, после `await()` |

Общая часть здесь только чтение, а общей записи нет. Именно поэтому формулировка задания «взаимодействия потоков не требуется» выполняется буквально.

Общий индекс, куда пишут все потоки, и замок вокруг него это уже **ЛР4**.

## 8. Что нового по сравнению с ЛР2

| Что | Где в коде | Зачем |
|---|---|---|
| Создание потока на каждый файл | `new Thread(...).start()` в `main` | требование задания |
| Ожидание всех потоков | `CountDownLatch`, `countDown()`, `await()` | главный поток должен дождаться, прежде чем печатать |
| Свой индекс у каждого потока | список `partialIndexes`, `localIndex` | потоки не мешают друг другу, `synchronized` не нужен |
| Объединение индексов | цикл по `partialIndexes` после `await()` | собрать итоговый результат |
| `throws InterruptedException` | заголовок `main` | `await()` может выбросить это исключение |
| `try/finally` вокруг `processFile` | тело лямбды потока | гарантировать `countDown()` даже при ошибке |
| `permits` в регулярке | `DECLARATION` | корректный разбор sealed-классов (Java 17+) |
| `.distinct()` при выводе | печать результата | убрать повторы одноимённых детей |

Остальной код (`processFile`, `addParents`, `removeComments`, `removeGenerics`, обход папки) работает как в ЛР2. Единственное изменение в `processFile`: теперь он получает **свой** индекс, а не общий.

Про расхождение вывода с ЛР2 на Spring: две последние правки (`permits` и `distinct`) относятся не к многопоточности, а к качеству поиска. В ЛР2 sealed-объявления давали битые строки и ложных родителей, а повторы одноимённых детей были обычным делом (на Spring около 929). На проекте без sealed-классов и одноимённых классов вывод ЛР2 и ЛР3 совпадает побайтово.

## 9. Ограничения

- **Поток на файл.** На Spring Framework это около 10 тысяч потоков, и все запускаются почти сразу. Обычно работает, но на слабой машине возможна ошибка `unable to create native thread` (не хватает ресурсов на столько потоков). Ограничение числа потоков это тема **ЛР5** (`ExecutorService`).
- **Ключ индекса простое имя.** Одноимённые классы из разных пакетов (например, несколько `Builder`) сливаются в одну запись. `distinct()` только убирает повторы в выводе, а не различает такие классы.
- **Регулярка не обрабатывает** `enum` и `record`, а на редких конструкциях может сработать ошибочно. Для лабораторной этого достаточно.
- **Комментарии** вырезаются упрощённо (см. 5.7).

## 11. Что говорить на защите

Основная идея одной фразой:

> Каждый поток обрабатывает свой файл и пишет в свой собственный индекс. Потоки не используют общих изменяемых данных, поэтому синхронизация не нужна. Главный поток дожидается всех потоков с помощью `CountDownLatch`, затем объединяет частичные индексы в один и печатает результат.

Возможные вопросы и ответы:

**Зачем `CountDownLatch`, а не `join()`?**
`join()` пришлось бы вызывать у каждого потока по отдельности, для этого нужно хранить все объекты `Thread`. Защёлка проще: каждый поток сообщает о завершении, главный ждёт одним вызовом `await()`.

**Зачем `try/finally`?**
Чтобы `countDown()` выполнялся, даже если поток завершился ошибкой. Иначе главный поток завис бы на `await()`.

**Почему нет `synchronized`?**
Потоки не пишут в общие данные: у каждого свой индекс. Результаты объединяет главный поток после завершения всех остальных. Общий индекс с блокировкой это задание 4.

**Почему индексы создаются до запуска потоков?**
Чтобы список индексов не менялся, пока потоки работают. Тогда потоки вообще не обращаются к общему списку.

**Зачем отдельные переменные `file` и `localIndex` внутри цикла?**
Лямбда потока выполняется позже, а переменная цикла `i` к тому времени изменится. Java разрешает использовать в лямбде только не изменяющиеся переменные. `file` и `localIndex` создаются заново на каждом шаге и больше не меняются.

**Чем `start()` отличается от `run()`?**
`start()` запускает новый поток, а `run()` просто выполнит код в текущем потоке.

**Почему главный поток видит результаты потоков?**
`CountDownLatch` гарантирует, что действия потока до `countDown()` видны потоку, который вернулся из `await()`.

**Какие недостатки у подхода «поток на файл»?**
Тысячи потоков создают большие накладные расходы и могут исчерпать ресурсы. Решение в ЛР5 это ограниченный пул потоков.

**Что изменилось по сравнению с ЛР2 в разборе объявлений?**
Регулярка дополнена обработкой `permits` (sealed-классы Java 17+), при выводе добавлен `distinct()`, так как индекс ключуется по простому имени класса и в большом проекте одноимённые классы дают повторы.

## 12. Глоссарий

| Термин | Значение |
|---|---|
| Поток (`Thread`) | независимый исполнитель кода внутри программы |
| Главный поток | поток, в котором выполняется `main` |
| Гонка данных | ошибка, когда несколько потоков одновременно меняют одни данные |
| Синхронизация | механизм, не дающий потокам менять данные одновременно (ЛР4) |
| `CountDownLatch` | счётчик, на котором можно ждать, пока он дойдёт до нуля |
| Лямбда | короткая безымянная функция: `x -> x + 1` |
| Effectively final | переменная, которой значение присвоено один раз и больше не меняется |
| Stream | конвейер обработки данных: `filter`, `map`, `collect` |
| Обобщения (generics) | угловые скобки с типами: `List<String>` |
| `List` | интерфейс списка; `ArrayList` его реализация |
| `Map` | словарь «ключ значение»; `TreeMap` хранит ключи отсортированными |
| `static` | принадлежит классу, а не объекту |
| `final` | значение нельзя изменить после присвоения |
| `null` | «ничего нет», пустая ссылка |
| Регулярное выражение | шаблон для поиска текста |
| Группа в регулярке | часть шаблона в скобках, содержимое которой можно получить через `group(n)` |
| Ленивый квантор | `+?` или `*?`: берёт минимум символов |
| Исключение | сигнал об ошибке; ловится в `catch` |
| `try-with-resources` | `try (...)`, который сам закрывает ресурс |
| Обратный индекс | словарь «родитель список детей» |
