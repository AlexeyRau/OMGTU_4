# Лабораторная работа №3. Поисковый робот с независимыми потоками

Полный разбор программы `InheritanceIndexThreads.java`: что делает каждая строка и чем версия отличается от лабораторной №2.

> Сравнение идёт с `lab_2` (предыдущая лабораторная, задание 2).

---

## 1. Что программа делает в целом

Программа строит **обратный индекс наследования**: для каждого класса/интерфейса-родителя печатает список его детей.

Пример из `lab_2/test_project`:

```java
class Base {}
class Both extends Base implements Flyable {}
interface Flyable {}
```

Вывод:

```
Base <- Both
Flyable <- Both
```

Ключ — родитель (`Base`), значение — список детей (`Both`).

Алгоритм:

```
1. Найти все .java файлы в папке
2. На каждый файл — отдельный поток
3. Каждый поток читает свой файл и строит СВОЙ маленький индекс
4. Главный поток ждёт, пока все потоки закончат
5. Главный поток сливает маленькие индексы в один большой
6. Печатает большой индекс
```

Ключевая идея задания 3: потоки **ничего не делят**, поэтому синхронизация не нужна. Общий результат собирается уже после того, как все потоки завершились.

## 2. Немного терминов Java

- **Класс** — структура с данными и функциями. Здесь один класс `InheritanceIndexThreads`.
- **Метод** — функция внутри класса. `main` — точка входа, `processFile`, `addParents` — вспомогательные.
- **`static`** — метод/поле принадлежит классу, а не объекту. Объект (`new InheritanceIndexThreads()`) не создаётся.
- **`private`** — видно только внутри класса.
- **Generics** — `<String>` и т.п. означают «коллекция строк», «словарь строка → список строк». Проверяется компилятором.
- **`Map<K, V>`** — словарь: ключ → значение. `TreeMap` — словарь, который хранит ключи **отсортированными**.
- **`List<T>`** — список с доступом по индексу. `ArrayList` — его обычная реализация.
- **Лямбда** `() -> { ... }` — короткая запись функции (анонимный метод).
- **Stream API** — цепочки операций над коллекциями: `filter` (отобрать), `map` (преобразовать), `collect` (собрать).
- **Исключение** — объект-ошибка. `IOException` — ошибка ввода-вывода (файл не читается).

### Строки 17–22: регулярное выражение

```java
private static final Pattern DECLARATION = Pattern.compile(
    "\\b(class|interface)\\s+(\\w+)\\s*"
    + "(?:extends\\s+([^{]+?))?\\s*"
    + "(?:implements\\s+([^{]+?))?\\s*"
    + "(?:permits\\s+[^{]+?)?\\s*\\{"
);
```

- `private static final` — одна общая константа на весь класс, создаётся один раз.
- `Pattern.compile(...)` — «компилирует» regex в быстрый автомат. Это дорого, поэтому делается один раз, а не в каждом потоке. `Pattern` можно безопасно использовать из нескольких потоков.
- В Java-строках `\\` — это один обратный слэш в самом regex (потому что `\` в строке — спецсимвол).

Разбор regex по частям:

| Часть | Что значит |
|---|---|
| `\b` | граница слова: `class` в `superclass` не сработает |
| `(class\|interface)` | группа 1: ключевое слово `class` или `interface` |
| `\s+` | один или больше пробельных символов (пробел, таб, перенос строки) |
| `(\w+)` | группа 2: имя класса — буквы, цифры, `_` |
| `\s*` | ноль или больше пробельных символов |
| `(?:extends\s+([^{]+?))?` | необязательный блок `extends ...`; группа 3 — список родителей |
| `(?:implements\s+([^{]+?))?` | необязательный блок `implements ...`; группа 4 — список интерфейсов |
| `(?:permits\s+[^{]+?)?` | необязательный блок `permits ...` (для `sealed`), просто пропускается |
| `\s*\{` | ноль+ пробелов и открывающая фигурная скобка тела класса |

Что такое `[^{]+?`:

- `[^{]` — любой символ, кроме `{`;
- `+` — один или больше;
- `?` после `+` — «ленивый»: захватить как можно меньше, но так, чтобы остальная часть regex совпала.

Пример:

```java
class Both extends Base implements Flyable {
```

- группа 1 = `class`
- группа 2 = `Both`
- группа 3 = `Base`
- группа 4 = `Flyable`

`(?: ... )` — необязательная группа, которая не сохраняет результат (сам текст `extends` не нужен).

`\s*` перед `{` нужен, потому что между `implements Flyable` и `{` может быть перенос строки, табы и т.п.

Ограничения (для задания допустимы):

- `@interface Foo` тоже совпадёт, потому что `@` — не буква; получится «интерфейс» без родителей, на вывод это не влияет;
- `class` внутри строковых литералов может дать ложное срабатывание (комментарии вырезаются, строки — нет);
- `enum` и `record` не индексируются — задание требует только `class`/`interface`.

### Строки 27–33: сбор списка `.java` файлов

```java
List<Path> javaFiles;
try (Stream<Path> paths = Files.walk(root)) {
    javaFiles = paths
            .filter(p -> Files.isRegularFile(p))
            .filter(p -> p.toString().endsWith(".java"))
            .collect(Collectors.toList());
}
```

- `List<Path> javaFiles;` — объявлен список путей. Пока пустой.
- `Files.walk(root)` — рекурсивно обходит папку и отдаёт **поток** всех путей (файлы + подпапки).
- `try ( ... ) { ... }` — try-with-resources: после выхода из блока `paths` автоматически закроется. Для `Files.walk` это важно: он держит открытым дескриптор директории.
- `.filter(p -> Files.isRegularFile(p))` — оставить только обычные файлы (не папки).
- `.filter(p -> p.toString().endsWith(".java"))` — оставить только `.java`.
- `.collect(Collectors.toList())` — «материализовать» поток в `ArrayList`.

Почему сначала собирается список, а не запускаются потоки прямо в обходе:

1. нужно знать **точное количество** файлов, чтобы создать `CountDownLatch` с правильным счётчиком;
2. нужно заранее создать по индексу на каждый файл и раздать их потокам.

### Строки 35–39: по отдельному индексу на файл

```java
// У каждого файла (потока) свой отдельный индекс: потоки ничего не разделяют
List<Map<String, List<String>>> partialIndexes = new ArrayList<>();
for (int i = 0; i < javaFiles.size(); i++) {
    partialIndexes.add(new TreeMap<>());
}
```

Тип читается с конца:

- `String` — имя класса;
- `List<String>` — список имён детей;
- `Map<String, List<String>>` — словарь «родитель → дети»;
- `List<...>` — список таких словарей, по одному на файл.

То есть `partialIndexes.get(0)` — индекс, построенный по первому файлу, `get(1)` — по второму, и т.д.

- `new ArrayList<>()` — пустой список. `<>` (diamond) говорит компилятору: «тип элемента возьми из объявления слева».
- `new TreeMap<>()` — пустой отсортированный словарь.
- Цикл `for (int i = 0; ...)` — обычный счётчик.

Почему список, а не массив: в Java нельзя создать массив generic-типа (`new Map<String, List<String>>[n]` — ошибка компиляции), а `List` можно.

### Строки 41–52: запуск потока на каждый файл

```java
CountDownLatch latch = new CountDownLatch(javaFiles.size());
```

- Создаётся защёлка со счётчиком, равным числу файлов, например 9293.
- Внутри — атомарный счётчик. `countDown()` уменьшает на 1, `await()` блокирует поток, пока счётчик не станет 0.
- Латч одноразовый: после нуля его нельзя «перезарядить».

```java
for (int i = 0; i < javaFiles.size(); i++) {
    Path file = javaFiles.get(i);
    Map<String, List<String>> localIndex = partialIndexes.get(i);
```

- `file` — очередной файл.
- `localIndex` — **его собственный** словарь из `partialIndexes`.
- Обе переменные объявлены **внутри** тела цикла, поэтому на каждой итерации создаются заново.

```java
    new Thread(() -> {
        try {
            processFile(file, localIndex);
        } finally {
            latch.countDown();
        }
    }).start();
}
```

- `() -> { ... }` — лямбда без параметров. Она реализует интерфейс `Runnable`, у которого один метод `run()`.
- `new Thread(runnable)` — создаёт объект потока.
- `.start()` — **запускает** новый поток, и уже он выполняет `run()`. Если вызвать `.run()` напрямую, код выполнится в текущем (главном) потоке — параллельности не будет.
- `try/finally`: `finally` выполнится **всегда** — и при успехе, и если `processFile` бросит исключение. Поэтому `latch.countDown()` обязательно произойдёт, и главный поток не зависнет.
- Ссылка на `Thread` не сохраняется — она не нужна, потому что ожидание идёт не через `join()`, а через латч.

Почему лямбда может использовать `file` и `localIndex`:

- Java разрешает захватывать в лямбду только **effectively final** переменные — те, которые не меняются после присваивания.
- `file` и `localIndex` создаются заново каждую итерацию и внутри не меняются, поэтому каждая лямбда захватывает свою пару.
- Если бы использовался `i` внутри лямбды — была бы ошибка компиляции: `i` меняется (`i++`).

Почему каждый поток пишет в свою map:

- `partialIndexes.get(0)` трогает только поток №0, `get(1)` — только поток №1.
- Общих изменяемых данных нет → **гонок данных нет** → `synchronized` не нужен.
- Именно этого требует задание: «взаимодействия потоков не требуется».

### Строка 53: ожидание всех потоков

```java
latch.await();
```

- Главный поток блокируется, пока счётчик не станет 0, т.е. пока все потоки не вызовут `countDown()`.
- Если файлов 0, счётчик уже 0 — `await()` сразу вернётся.
- `InterruptedException` — если главный поток прервут, `await()` бросит это исключение (объявлено в `main`).

**Почему после `await()` можно безопасно читать map без синхронизации:**

В Java есть формальное правило *happens-before*: всё, что поток сделал до `countDown()`, гарантированно видно потоку, который успешно вернулся из `await()`. То же самое гарантирует `Thread.start()` для кода до запуска. Это не «повезло», а гарантия модели памяти Java.

### Строки 55–62: слияние частичных индексов

```java
Map<String, List<String>> index = new TreeMap<>();
for (Map<String, List<String>> partial : partialIndexes) {
    partial.forEach((parent, children) -> {
        List<String> all = index.getOrDefault(parent, new ArrayList<>());
        all.addAll(children);
        index.put(parent, all);
    });
}
```

- `index` — итоговый словарь. `TreeMap` хранит ключи отсортированными, поэтому вывод всегда в алфавитном порядке.
- `for (Map<...> partial : partialIndexes)` — цикл «для каждого элемента списка».
- `partial.forEach((parent, children) -> { ... })` — пройти по всем парам «ключ → значение» этого словаря.
- `index.getOrDefault(parent, new ArrayList<>())`:
  - если `parent` уже есть в итоговом словаре — вернуть его список детей;
  - если нет — вернуть новый пустой список (и **не** добавлять его в словарь).
- `all.addAll(children)` — добавить всех детей из частичного индекса.
- `index.put(parent, all)` — положить список обратно в словарь. Для нового родителя это и создаёт запись; для существующего — заменяет тем же самым объектом списка.

Именно `getOrDefault()` требует задание 2 — здесь он используется по назначению.

Слияние делает **один главный поток**, поэтому здесь тоже не нужна синхронизация. Заодно результат детерминирован: один и тот же набор файлов даёт один и тот же вывод.

### Строки 64–70: печать

```java
index.forEach((parent, children) -> {
    String line = children.stream()
            .distinct()
            .sorted()
            .collect(Collectors.joining(", "));
    System.out.println(parent + " <- " + line);
});
```

- `index.forEach(...)` — по всем родителям в отсортированном порядке (свойство `TreeMap`).
- `children.stream()` — поток имён детей.
- `.distinct()` — убрать повторы (использует `equals`; у `String` он сравнивает содержимое).
- `.sorted()` — отсортировать по алфавиту.
- `.collect(Collectors.joining(", "))` — склеить в одну строку через запятую с пробелом.
- `parent + " <- " + line` — конкатенация строк.
- `System.out.println(...)` — печать в stdout с переводом строки.

Почему `.distinct()`: индекс ключуется по **простому** имени. В большом проекте есть разные классы с одинаковым именем в разных пакетах, и без `distinct()` получаются строки вида `A <- ..., B, B, C, C`. На Spring таких повторов было 929.

### Строки 73–91: обработка одного файла

```java
private static void processFile(Path file, Map<String, List<String>> index) {
```

- `private static void` — вспомогательный метод класса, ничего не возвращает.
- `file` — какой файл читать.
- `index` — **локальный** словарь этого потока, куда писать результат.

```java
    String text;
    try {
        text = Files.readString(file);
    } catch (IOException e) {
        System.err.println("Не удалось прочитать файл: " + file);
        return;

```

- `Files.readString(file)` — читает весь файл в строку (по умолчанию UTF-8).
- Если файл недоступен/битый — сообщение в `System.err` (stderr, отдельный поток вывода для ошибок) и выход из метода.
- Важно: `return` выйдет из `processFile`, но `finally` в потоке всё равно вызовет `countDown()`, так что латч не зависнет.

```java
    text = removeComments(text);
    text = removeGenerics(text);
```

- Сначала убираются комментарии: в них могут быть «фальшивые» объявления классов и символы `<`/`>`.
- Потом убираются generic-параметры, чтобы regex не путался на `Container<Map<String, List<Integer>>>`.

```java
    Matcher m = DECLARATION.matcher(text);
    while (m.find()) {
        String child = m.group(2);
        addParents(index, child, m.group(3));
        addParents(index, child, m.group(4));
    }
}
```

- `DECLARATION.matcher(text)` — создать искалку для конкретного текста. `Matcher` не потокобезопасен, но он создаётся внутри каждого вызова — у каждого потока свой.
- `while (m.find())` — искать следующее совпадение; `find()` возвращает `false`, когда совпадений больше нет.
- `m.group(2)` — имя класса-ребёнка.
- `m.group(3)` — текст после `extends` (или `null`, если его нет).
- `m.group(4)` — текст после `implements` (или `null`).
- `addParents` вызывается дважды: один раз для extends, второй для implements.

### Строки 93–106: добавление родителей в словарь

```java
private static void addParents(Map<String, List<String>> index, String child, String parentsText) {
    if (parentsText == null) {
        return;
    }
```

- Если блока `extends`/`implements` не было, `group(3)`/`group(4)` вернёт `null` — просто выход.

```java
    Arrays.stream(parentsText.split(","))
            .map(String::trim)
            .filter(name -> !name.isEmpty())
            .map(name -> name.substring(name.lastIndexOf('.') + 1))
            .forEach(parent -> {
                List<String> children = index.getOrDefault(parent, new ArrayList<>());
                children.add(child);
                index.put(parent, children);
            });
}
```

- `parentsText.split(",")` — разбить список через запятую: `"A, B"` → `["A", " B"]`.
- `Arrays.stream(...)` — превратить массив в поток.
- `.map(String::trim)` — убрать пробелы по краям. `String::trim` — method reference, короткая запись `s -> s.trim()`.
- `.filter(name -> !name.isEmpty())` — выбросить пустые куски (например, от лишней запятой).
- `.map(name -> name.substring(name.lastIndexOf('.') + 1))` — оставить только простое имя:
  - `java.util.ArrayList` → `ArrayList`;
  - `Map.Entry` → `Entry`;
  - `Base` (точек нет) → `Base`, потому что `lastIndexOf('.')` вернёт `-1`, а `substring(0)` — вся строка.
- `.forEach(parent -> { ... })` — для каждого родителя:
  - `getOrDefault` — взять существующий список детей или создать новый;
  - `add(child)` — добавить ребёнка;
  - `put` — сохранить обратно.

Здесь `index` — это **локальный** словарь потока, поэтому `synchronized` не нужен.

### Строки 108–110: удаление комментариев

```java
private static String removeComments(String text) {
    return text.replaceAll("(?s)/\\*.*?\\*/", "").replaceAll("//.*", "");
}
```

- `replaceAll(regex, replacement)` — заменить все совпадения.
- `(?s)` — флаг DOTALL: точка `.` начинает совпадать и с переводом строки (нужно для многострочных `/* ... */`).
- `/\*.*?\*/` — блочный комментарий:
  - `/\*` — литерал `/*` (звёздочку надо экранировать);
  - `.*?` — «лениво» любой текст, включая переносы;
  - `\*/` — закрывающие `*/`.
- `//.*` — строчный комментарий до конца строки (точка не матчит `\n`, поэтому замена не съедает следующую строку).
- Вызовы сцеплены: сначала вырезаются блочные, потом строчные.

Ограничение: если в строковом литерале встретится `"http://..."`, всё после `//` в этой строке будет вырезано. Для задачи это почти безвредно, но знать стоит.

### Строки 112–119: удаление generic-параметров

```java
private static String removeGenerics(String text) {
    String previous;
    do {
        previous = text;
        text = text.replaceAll("<[^<>]*>", "");
    } while (!text.equals(previous));
    return text;
}
```

- `<[^<>]*>` — найти пару угловых скобок **без вложенных** скобок внутри: `<String>`, `<Map.Entry>` и т.п.
- Проблема: `<Map<String, List<Integer>>>` содержит вложенные скобки. За один проход внутренние не удалятся корректно.
- Поэтому цикл `do ... while`: повторять, пока строка меняется.
  1. первый проход убирает `<String>` и `<Integer>`;
  2. второй — `<Map, List>`;
  3. третий — внешние `<...>`;
  4. когда замен не было (`text.equals(previous)`), выход.
- `previous` хранит строку до прохода, чтобы сравнить.

Зачем вообще: после удаления generics объявления становятся простыми:

```java
class Container<T> extends Base {}
// превращается в
class Container extends Base {}
```

и regex надёжно видит `extends Base {`.

Ограничение: глобальная замена может испортить сравнения `a < b && c > d` в телах методов. На объявления классов это обычно не влияет, но это «эвристика», а не настоящий парсер Java.

## 5. Как это работает по шагам (таймлайн)

1. Главный поток разбирает аргументы и получает путь.
2. Рекурсивно собирает все `.java` в `javaFiles`.
3. Создаёт `partialIndexes` — пустые словари, по одному на файл.
4. Создаёт `latch` со счётчиком `N = число файлов`.
5. В цикле для каждого файла:
   - берёт его путь и его пустой словарь;
   - создаёт поток;
   - поток читает файл, чистит комментарии/generics, ищет объявления, пишет родителей в **свой** словарь;
   - в `finally` уменьшает счётчик.
6. Главный поток вызывает `latch.await()` и спит, пока счётчик не 0.
7. Просыпается, когда все файлы обработаны.
8. Сливает все `partialIndexes` в один `TreeMap`, попутно склеивая списки детей.
9. Печатает: для каждого родителя — отсортированных уникальных детей.

## 7. Вероятные вопросы на защите

**— Почему нет `synchronized`?**
Каждый поток пишет только в свой словарь. Общих изменяемых данных нет. Общий индекс собирается в главном потоке после `await()`. Это ровно условие задания «взаимодействие потоков не требуется». `synchronized` здесь был бы решением задания 4.

**— Почему `CountDownLatch`, а не `join()`?**
Латч позволяет дождаться N завершений, не храня ссылки на потоки. `countDown()` стоит в `finally`, поэтому счётчик уменьшится даже при ошибке чтения файла.

**— Почему `countDown()` в `finally`?**
Чтобы при исключении внутри `processFile` главный поток не ждал вечно.

**— Почему `start()`, а не `run()`?**
`start()` создаёт новый поток и в нём вызывает `run()`. Прямой `run()` выполнил бы код в текущем потоке — никакой параллельности.

**— Что будет, если папка пустая?**
`CountDownLatch(0)`, `await()` сразу вернётся, индекс пустой, ничего не напечатается.

**— Что будет, если файл не читается?**
Поток напечатает ошибку в stderr, его локальный словарь останется пустым, `finally` уменьшит счётчик. Остальные файлы обработаются.

**— Почему `TreeMap`, а не `HashMap`?**
`TreeMap` хранит ключи отсортированными → вывод детерминированный и читаемый.

**— Почему результат совпадает с однопоточной версией?**
Потоки обрабатывают независимые файлы, а слияние идёт в фиксированном порядке. Набор пар «родитель → ребёнок» тот же.

**— Где здесь гонка данных?**
Её нет: `partialIndexes` заполняется до старта потоков, каждый поток трогает только свой элемент, главный читает после `await()` (гарантия happens-before).

**— Зачем `distinct()`?**
Индекс по простым именам: в большом проекте одноимённые классы дают повторяющихся детей. Без него на Spring 929 дублей.

**— Зачем `permits` в regex?**
Чтобы `sealed interface X extends Y permits A, B {` не затягивал список `permits` в родителей.

**— Почему один поток на файл — это плохо для 100k файлов?**
Создание потока дорогое, память под стек, переключения контекста. Для этого есть пул потоков — задание 5 (`ExecutorService`).

**— Почему скорость выросла всего в ~1.3 раза?**
Задача упирается в чтение файлов и создание 9293 потоков; слияние однопоточное. Пул потоков из задания 5 уменьшит накладные расходы.

## 8. Ограничения, которые стоит знать

1. Это **не настоящий парсер Java**, а regex-эвристика: строковые литералы не вырезаются, `@interface` считается интерфейсом, `enum`/`record` не индексируются, аннотации с параметрами могут сбить совпадение.
2. `removeComments` может испортить строку с `//` внутри литерала.
3. `removeGenerics` глобально удаляет `<...>`, что теоретически может задеть сравнения в коде.
4. Индекс по простым именам: `a.b.Foo` и `c.d.Foo` не различаются.
5. Один поток на файл не масштабируется на сотни тысяч файлов.
6. Потоки не именуются и не сохраняются — отладка сложнее, зато код проще.
