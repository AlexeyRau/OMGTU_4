# Лабораторная работа №4. Поисковый робот с синхронизацией доступа потоков к данным

Полный разбор программы `InheritanceIndexLock.java`: что делает каждая строка и каждая функция, как устроена синхронизация и чем эта лабораторная отличается от ЛР3.

> Сравнение идёт с `lab_3/InheritanceIndexThreads.java` (ЛР3 — «поисковый робот с независимыми потоками»).

---

## 1. Что программа делает в целом

Программа строит **обратный индекс наследования** по всем `.java` файлам проекта: для каждого класса/интерфейса-родителя печатает список его детей.

Пример:

```java
class Base {}
class Both extends Base implements Flyable {}
interface Flyable {}
```

Вывод:

```
Base <- Both
Flyable <- Both
```

Алгоритм:

```
1. Найти все .java файлы в папке
2. Создать ОДИН общий индекс (Map) и ОДИН объект синхронизации (ReentrantLock)
3. На каждый файл запустить отдельный поток
4. Каждый поток читает свой файл, разбирает объявления и пишет результат
   в ОБЩИЙ индекс, захватывая лок на время записи
5. Главный поток ждёт завершения всех потоков через join()
6. Главный поток печатает общий индекс
```

Главное отличие от ЛР3: там потоки были полностью независимы (у каждого свой индекс), а здесь они **намеренно работают с общими данными**, поэтому запись защищена `ReentrantLock`.

## 2. Термины, которые нужны для понимания

- **Поток (Thread)** — независимая последовательность выполнения. Несколько потоков могут работать одновременно.
- **Общие данные (shared state)** — объект, к которому обращаются несколько потоков. Здесь это `index`.
- **Гонка данных (data race)** — ситуация, когда два потока одновременно меняют одни и те же данные, и результат зависит от порядка/удачи.
- **Критическая секция** — участок кода, который должен выполняться только одним потоком за раз.
- **Мьютекс / лок** — «замок»: поток захватывает его, работает с общими данными, отпускает. Остальные ждут.
- **`ReentrantLock`** — реализация такого лока из `java.util.concurrent.locks`. «Reentrant» значит, что один и тот же поток может захватить его повторно (и должен столько же раз отпустить).
- **`join()`** — метод потока: «дождись, пока этот поток завершится».
- **happens-before** — формальная гарантия модели памяти Java: если поток A завершился, а поток B сделал `join()` для A, то B видит все изменения, сделанные A.
- **`Map<K, V>`** — словарь «ключ → значение». `TreeMap` — словарь, который хранит ключи отсортированными. **Он не потокобезопасен.**
- **`List<T>`** — список. `ArrayList` — обычная реализация, тоже **не потокобезопасна**.
- **Лямбда** `() -> { ... }` — короткая запись функции (здесь — тела потока).
- **Stream API** — цепочки операций над коллекциями: `filter`, `map`, `forEach`, `collect`.

### Строки 17–22: регулярное выражение

```java
private static final Pattern DECLARATION = Pattern.compile(
    "\\b(class|interface)\\s+(\\w+)\\s*"
    + "(?:extends\\s+([^{]+?))?\\s*"
    + "(?:implements\\s+([^{]+?))?\\s*"
    + "(?:permits\\s+[^{]+?)?\\s*\\{"
);
```

- `private static final` — одна константа на весь класс, создаётся один раз.
- `Pattern.compile(...)` — компиляция regex в быстрый автомат (дорогая операция, поэтому один раз). `Pattern` потокобезопасен.
- `\\` в Java-строке — это один `\` в самом regex.

Разбор по частям:

| Часть | Что значит |
|---|---|
| `\b` | граница слова: `class` внутри `superclass` не сработает |
| `(class\|interface)` | группа 1: ключевое слово |
| `\s+` | один или больше пробельных символов |
| `(\w+)` | группа 2: имя класса |
| `(?:extends\s+([^{]+?))?` | необязательный `extends ...`; группа 3 — родители |
| `(?:implements\s+([^{]+?))?` | необязательный `implements ...`; группа 4 — интерфейсы |
| `(?:permits\s+[^{]+?)?` | необязательный `permits ...` (для `sealed`), пропускается |
| `\s*\{` | пробелы и `{` — начало тела класса |

`[^{]+?` — «лениво» захватить как можно меньше любых символов, кроме `{`.

Пример:

```java
class Both extends Base implements Flyable {
```

- группа 1 = `class`;
- группа 2 = `Both`;
- группа 3 = `Base`;
- группа 4 = `Flyable`.

### Строки 27–33: сбор всех `.java` файлов

```java
List<Path> javaFiles;
try (Stream<Path> paths = Files.walk(root)) {
    javaFiles = paths
            .filter(p -> Files.isRegularFile(p))
            .filter(p -> p.toString().endsWith(".java"))
            .collect(Collectors.toList());
}
```

- `Files.walk(root)` — рекурсивный обход папки, отдаёт **поток** путей.
- `try (...)` — try-with-resources: после блока поток автоматически закрывается (освобождает дескриптор директории).
- `filter(p -> Files.isRegularFile(p))` — оставить только файлы.
- `filter(p -> p.toString().endsWith(".java"))` — только `.java`.
- `collect(Collectors.toList())` — собрать в `ArrayList`.

Список нужен, чтобы:

1. пройти по файлам и создать потоки;
2. сохранить ссылки на потоки в `threads`, чтобы потом сделать `join()`.

### Строки 35–37: общий индекс и лок

```java
// Единый индекс и объект синхронизации, который защищает доступ к нему
Map<String, List<String>> index = new TreeMap<>();
ReentrantLock lock = new ReentrantLock();
```

- `index` — **один на всю программу** словарь «родитель → список детей».
- `new TreeMap<>()` — пустой отсортированный словарь. `TreeMap`, как и `ArrayList`, **не является потокобезопасным**: одновременная запись из нескольких потоков может его сломать.
- `lock` — объект-замок. Именно он будет защищать `index`.
- Оба объекта создаются **до** запуска потоков и потом только читаются/используются (сами переменные не переприсваиваются).

### Строки 39–44: запуск потока на каждый файл

```java
List<Thread> threads = new ArrayList<>();
for (Path file : javaFiles) {
    Thread thread = new Thread(() -> processFile(file, index, lock));
    threads.add(thread);
    thread.start();
}
```

- `threads` — список, куда складываются все созданные потоки. Он нужен для `join()`: чтобы дождаться потока, нужна ссылка на него.
- `for (Path file : javaFiles)` — цикл «для каждого файла».
- `new Thread(...)` — создаёт объект потока.
- `() -> processFile(file, index, lock)` — лямбда, реализующая `Runnable.run()`. Когда поток запустится, он выполнит `processFile` с общим индексом и общим локом.
- `threads.add(thread)` — сохранить ссылку.
- `thread.start()` — запустить поток. Именно `start()`, а не `run()`: `run()` выполнил бы код в текущем потоке, без параллельности.

Почему лямбда может использовать `file`, `index`, `lock`:

- Java разрешает захватывать только **effectively final** переменные.
- `file` — переменная цикла, внутри не меняется.
- `index` и `lock` присвоены один раз и больше не меняются.
- Если бы мы попытались захватить изменяемую переменную (например, `i++`), компилятор выдал бы ошибку.

### Строки 46–49: ожидание завершения всех потоков

```java
// Главный поток ждёт завершения всех потоков
for (Thread thread : threads) {
    thread.join();
}
```

- `join()` блокирует текущий (главный) поток, пока поток `thread` не завершится.
- Если поток уже закончил — `join()` вернётся сразу.
- `join()` может бросить `InterruptedException`, поэтому оно объявлено в `main`.
- После завершения всех `join()` главный поток гарантированно **видит** все изменения, сделанные рабочими потоками (правило happens-before). Поэтому печатать индекс можно без лока.

### Строки 51–57: печать индекса

```java
index.forEach((parent, children) -> {
    String line = children.stream()
            .distinct()
            .sorted()
            .collect(Collectors.joining(", "));
    System.out.println(parent + " <- " + line);
});
```

- `index.forEach(...)` — пройти по всем парам «родитель → дети»; `TreeMap` отдаёт ключи по алфавиту.
- `children.stream()` — поток имён детей.
- `.distinct()` — убрать повторы (в больших проектах бывают одноимённые классы).
- `.sorted()` — отсортировать по алфавиту.
- `.collect(Collectors.joining(", "))` — склеить в строку через запятую.
- `System.out.println(...)` — печать с переводом строки.

Печать выполняется **после** `join()`, когда рабочих потоков уже нет. Лок здесь не нужен: гонки с ними невозможны.

### Строки 60–67: чтение одного файла

```java
private static void processFile(Path file, Map<String, List<String>> index, ReentrantLock lock) {
    String text;
    try {
        text = Files.readString(file);
    } catch (IOException e) {
        System.err.println("Не удалось прочитать файл: " + file);
```

- `private static void` — вспомогательный метод класса, ничего не возвращает.
- Параметры:
  - `file` — какой файл обрабатывать;
  - `index` — **общий** индекс (один для всех потоков);
  - `lock` — **общий** лок, которым защищается индекс.
- `Files.readString(file)` — читает файл в строку (UTF-8).
- При ошибке — сообщение в `System.err` и `return`. Поток при этом просто завершится, остальные продолжат работу.

### Строки 72–77: поиск объявлений

```java
    Matcher m = DECLARATION.matcher(text);
    while (m.find()) {
        String child = m.group(2);
        addParents(index, lock, child, m.group(3));
        addParents(index, lock, child, m.group(4));
    }

```

- `DECLARATION.matcher(text)` — создать искалку для этого текста. `Matcher` не потокобезопасен, но у каждого потока он свой.
- `while (m.find())` — перебирать совпадения, пока они есть.
- `m.group(2)` — имя класса-ребёнка (группа 2 regex).
- `m.group(3)` — текст после `extends` или `null`.
- `m.group(4)` — текст после `implements` или `null`.
- `addParents` вызывается дважды: для `extends` и для `implements`.
- Здесь начинается работа с общим индексом — через `addParents`, где и стоит лок.

### Строки 80–84: сигнатура `addParents` и проверка на `null`

```java
private static void addParents(Map<String, List<String>> index, ReentrantLock lock,
                               String child, String parentsText) {
    if (parentsText == null) {
        return;
    }
```

- Метод добавляет в индекс связи «родитель → child» для списка родителей.
- `parentsText == null` значит, что блока `extends`/`implements` не было — делать нечего.
- `lock` передаётся сюда, потому что именно здесь меняется общий `index`.

### Строки 85–89: разбор списка родителей

```java
    Arrays.stream(parentsText.split(","))
            .map(String::trim)
            .filter(name -> !name.isEmpty())
            .map(name -> name.substring(name.lastIndexOf('.') + 1))
```

- `parentsText.split(",")` — разбить `"A, B, C"` на массив `["A", " B", " C"]`.
- `Arrays.stream(...)` — массив → поток.
- `.map(String::trim)` — убрать пробелы по краям (`" B"` → `"B"`). `String::trim` — method reference.
- `.filter(name -> !name.isEmpty())` — выбросить пустые куски.
- `.map(name -> name.substring(name.lastIndexOf('.') + 1))` — оставить простое имя:
  - `java.util.ArrayList` → `ArrayList`;
  - `Map.Entry` → `Entry`;
  - `Base` → `Base` (`lastIndexOf('.')` вернёт `-1`, `substring(0)` — вся строка).

### Строки 89–98: критическая секция

```java
            .forEach(parent -> {
                lock.lock();
                try {
                    List<String> children = index.getOrDefault(parent, new ArrayList<>());
                    children.add(child);
                    index.put(parent, children);
                } finally {
                    lock.unlock();
                }
            });
}
```

Это **самое важное место лабораторной**.

- `lock.lock()` — захватить замок. Если его уже держит другой поток, текущий **блокируется и ждёт**, пока замок не освободят.
- `try { ... } finally { lock.unlock(); }` — гарантия, что замок будет отпущен даже при исключении. Если забыть `unlock()`, остальные потоки зависнут навсегда (deadlock).
- Внутри критической секции — три операции, которые обязаны выполниться **атомарно** (как одно целое):
  1. `getOrDefault` — взять список детей или создать новый;
  2. `children.add(child)` — добавить ребёнка;
  3. `index.put(parent, children)` — сохранить список в словарь.
- Почему нельзя защитить только `add`: между чтением и записью другой поток может вставить своего ребёнка, и изменения потеряются.
- Почему нельзя защитить только `put`: список мог быть получен до того, как другой поток его заменил.
- Замок один на весь индекс, а не на каждого родителя: это проще и надёжнее. Минус — записи разных потоков сериализуются, но критическая секция очень короткая (несколько обращений к памяти), а чтение и разбор файлов идут параллельно.

Тонкость: если `parent` уже есть в словаре, `getOrDefault` возвращает **тот самый** список, который лежит в `TreeMap`. `children.add(child)` меняет его напрямую, а `index.put` для существующего ключа фактически кладёт тот же объект обратно (не вредно). Если родителя не было — создаётся новый `ArrayList`, и `put` добавляет новую запись.

### Строки 101–103: удаление комментариев

```java
private static String removeComments(String text) {
    return text.replaceAll("(?s)/\\*.*?\\*/", "").replaceAll("//.*", "");
}
```

- `replaceAll(regex, "")` — удалить все совпадения.
- `(?s)` — DOTALL: `.` совпадает и с переводом строки (для многострочных `/* ... */`).
- `/\*.*?\*/` — блочный комментарий: `/*`, лениво любой текст, `*/`.
- `//.*` — строчный комментарий до конца строки.
- Сначала удаляются блочные, потом строчные.

Ограничение: `//` внутри строкового литерала (`"http://..."`) тоже будет вырезан. Для этой задачи это некритично.

### Строки 105–112: удаление generics

```java
private static String removeGenerics(String text) {
    String previous;
    do {
        previous = text;
        text = text.replaceAll("<[^<>]*>", "");
    } while (!text.equals(previous));
    return text;
}
```

- `<[^<>]*>` — пара угловых скобок без вложенных скобок.
- Вложенные generics (`<Map<String, List<Integer>>>`) удаляются за несколько проходов: сначала внутренние, потом внешние.
- Цикл `do ... while` повторяется, пока строка меняется.
- `previous` — строка до прохода, нужна для сравнения.

Зачем: после очистки объявление становится простым:

```java
class Container<T> extends Base {}
// → class Container extends Base {}
```

Ограничение: глобальная замена может задеть сравнения `a < b && c > d` в телах методов. На объявления классов это обычно не влияет.

## 4. Кратко о функциях

| Функция | Что делает |
|---|---|
| `main` | собирает файлы, создаёт общий индекс и лок, запускает потоки, ждёт через `join()`, печатает индекс |
| `processFile` | читает один файл, чистит комментарии/generics, ищет объявления через regex и передаёт родителей в `addParents` |
| `addParents` | разбирает список родителей, для каждого берёт лок и атомарно добавляет связь в общий индекс |
| `removeComments` | удаляет блочные и строчные комментарии |
| `removeGenerics` | удаляет `<...>`, включая вложенные, повторяя проходы |

## 5. Чем эта работа отличается от ЛР3

### Таблица

| Что | ЛР3 (`InheritanceIndexThreads`) | ЛР4 (`InheritanceIndexLock`) |
|---|---|---|
| Индекс | у каждого файла **свой** `TreeMap` | **один общий** `TreeMap` на всю программу |
| Синхронизация | отсутствует | `ReentrantLock` вокруг записи в индекс |
| Ожидание | `CountDownLatch` + `await()` | `join()` по списку потоков |
| Ссылки на потоки | не хранились | хранятся в `List<Thread>` |
| Результат | частичные индексы сливались после ожидания | потоки сразу пишут в общий индекс |
| Импорт | `CountDownLatch` | `ReentrantLock` |
| `main` | `throws IOException, InterruptedException` | то же самое |
| Парсер | одинаковый | одинаковый |
| Вывод | одинаковый | одинаковый |
| Смысл | потоки независимы, данные не разделяются | потоки разделяют данные, доступ защищён |

### Подробно

**1. Общий индекс вместо локальных.**

В ЛР3 было так:

```java
List<Map<String, List<String>>> partialIndexes = ...; // по одному на файл
...
processFile(file, localIndex);   // поток пишет только в свой словарь
...
// после await(): главный поток сливает всё в один index
```

В ЛР4:

```java
Map<String, List<String>> index = new TreeMap<>();   // один на всех
...
processFile(file, index, lock);   // поток пишет сразу в общий словарь
```

**2. Появилась синхронизация.**

В ЛР3 она была не нужна: потоки не пересекались по данным. В ЛР4 без лока несколько потоков одновременно меняют один `TreeMap`, а он не потокобезопасен. Поэтому появились `lock.lock()` / `lock.unlock()`.

**3. `join()` вместо `CountDownLatch`.**

В ЛР3 главный поток ждал счётчик:

```java
CountDownLatch latch = new CountDownLatch(javaFiles.size());
...
latch.countDown();
...
latch.await();
```

В ЛР4 он ждёт каждый поток:

```java
for (Thread thread : threads) {
    thread.join();
}
```

`join()` требует хранить ссылки на потоки, поэтому появился `List<Thread> threads`. Оба варианта корректны; задание 4 не требует латча, а `join()` здесь нагляднее.

**4. Что осталось тем же.**

- Регулярное выражение и разбор `class`/`interface`/`extends`/`implements`/`permits`.
- Удаление комментариев и generics.
- `getOrDefault()` при работе с `Map`.
- Сортировка и `distinct()` при печати.
- Формат вывода и результат: на `lab_2/test_project` и на Spring Framework вывод ЛР4 **побайтово совпадает** с ЛР3.

**5. Почему вывод не «портится» от порядка потоков.**

Список детей может пополняться в разном порядке, но перед печатью он сортируется (`.sorted()`), а дубли убираются (`.distinct()`). Поэтому итоговый текст детерминирован.

## 6. Таймлайн работы

1. Главный поток определяет корневую папку.
2. Рекурсивно собирает все `.java` в `javaFiles`.
3. Создаёт `index` (общий `TreeMap`) и `lock` (общий `ReentrantLock`).
4. Создаёт пустой список `threads`.
5. Для каждого файла:
   - создаёт поток, который вызовет `processFile(file, index, lock)`;
   - кладёт поток в `threads`;
   - запускает его через `start()`.
6. Каждый поток:
   - читает свой файл;
   - убирает комментарии и generics;
   - ищет объявления;
   - для каждого родителя захватывает лок, добавляет связь в общий индекс, отпускает лок;
   - завершается.
7. Главный поток по очереди вызывает `join()` для каждого потока и ждёт.
8. Когда все потоки завершились, главный поток печатает индекс.

## 8. Вероятные вопросы на защите

**— Зачем здесь лок, если в ЛР3 его не было?**
В ЛР3 у каждого потока был свой индекс, общих данных не было. В ЛР4 индекс один, и несколько потоков пишут в один `TreeMap`. Без лока возможны гонка данных и повреждение структуры.

**— Что будет, если убрать лок?**
Проверено экспериментально: на Spring Framework версия без лока падает с `NullPointerException` внутри `TreeMap.rotateRight` и теряет часть связей. С локом — стабильный результат.

**— Почему `ReentrantLock`, а не `synchronized`?**
Так рекомендует задание. Плюс у `ReentrantLock` явные `lock()/unlock()`, `tryLock()`, возможность честной очереди (`fair = true`) и другие возможности, которых нет у блока `synchronized`.

**— Почему лок стоит вокруг трёх операций, а не вокруг одной?**
`getOrDefault` + `add` + `put` — это одна логическая операция «добавить ребёнка». Если защитить только часть, другой поток может вклиниться между чтением и записью, и обновление потеряется.

**— Почему `unlock()` в `finally`?**
Чтобы замок освободился даже при исключении. Иначе поток завершится с ошибкой, замок останется захваченным, и остальные потоки зависнут.

**— Почему печать без лока?**
Все потоки уже завершены через `join()`, значит, никто больше не меняет индекс. `join()` даёт гарантию видимости изменений (happens-before).

**— Почему `join()`, а не `CountDownLatch`, как в ЛР3?**
Задание 4 не требует латча. Здесь потоки сохраняются в список, и `join()` — самый прямой способ дождаться каждого. Латч тоже подошёл бы.

**— Почему `TreeMap` не потокобезопасен?**
Это не синхронизированная коллекция: во время перебалансировки дерева другой поток может увидеть структуру в промежуточном состоянии. Поэтому нужен внешний лок.

**— Почему не `ConcurrentHashMap`?**
Можно было бы, но задание требует защитить доступ объектом синхронизации. Кроме того, операция «прочитать список, добавить в него, положить обратно» всё равно неатомарна, и для неё понадобился бы `compute`/лок.

**— Что такое реентерабельность `ReentrantLock`?**
Один и тот же поток может захватить лок повторно. Тогда `unlock()` нужно вызвать столько же раз, сколько было `lock()`. В этой программе повторного захвата нет.

**— Что будет, если файл не читается?**
Поток напечатает ошибку в stderr и завершится. Остальные файлы обработаются, индекс будет построен по доступным файлам.

**— Почему результат совпадает с ЛР3?**
Парсер одинаковый, а порядок добавления детей не важен: перед печатью список сортируется и очищается от дублей.

**— Почему время почти такое же, как в ЛР3?**
Лок держится очень коротко — только на добавление одной связи. Чтение файлов и разбор идут параллельно. На Spring: ЛР3 ~0.94 с, ЛР4 ~0.94–1.20 с.

## 9. Ограничения

1. Regex-парсер, а не настоящий разбор Java: строковые литералы не вырезаются, `@interface` считается интерфейсом, `enum`/`record` не индексируются.
2. `removeComments` может испортить строку с `//` внутри литерала.
3. `removeGenerics` глобально удаляет `<...>`, что теоретически может задеть сравнения в коде.
4. Индекс по простым именам: `a.b.Foo` и `c.d.Foo` не различаются.
5. Один поток на файл плохо масштабируется на сотни тысяч файлов (много потоков и переключений контекста). Это исправляется пулом потоков в следующей лабораторной.
6. Один глобальный лок сериализует записи. Здесь это не проблема из-за короткой критической секции, но при более тяжёлой обработке её стоило бы уменьшать.
